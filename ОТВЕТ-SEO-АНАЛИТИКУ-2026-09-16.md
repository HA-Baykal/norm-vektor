# Разбор заключения SEO-аналитика: что совпало, что нет, что исправлено

Дата: 2026-09-16
Повод: внешний SEO-аудит «P0: CSR → индексируемый HTML» (аналитик работал,
по его же словам, **без доступа к репозиторию**).

## TL;DR

- Рекомендацию «вариант А (Puppeteer-пререндер)» **внедрять не нужно**. Проект
  уже давно живёт по «варианту Б-лайт»: серверная отдача SEO-HTML через
  Vercel-функции `api/page.ts` и `api/seo.js` + автогенерация
  `vercel.json`/`sitemap.xml` при сборке. Пререндер поверх этого — параллельная
  система, которая будет конфликтовать с существующей (двойной источник
  мета-тегов и контента).
- Из 6 пунктов P0 аудита 5 уже закрыты в коде. **Шестой нашёлся реальный**:
  183 карточки товаров (`/kondicionery/:slug`, `/okna/:slug`) отдавали
  правильные мета-теги, но **тело `<body>` у всех было одинаковым — статический
  блок главной страницы из `index.html`**. Для Яндекса это 183 дубля главной.
  → Исправлено в этом коммите (`api/seo.js`).
- Добавлен инструментарий проверки: `npm run test:seo-fn` (локально, без сети)
  и `npm run check:seo` (продакшен глазами краулера, «до/после»).

## Почему диагноз аналитика не совпал с реальностью

Симптом из аудита: «view-source = `<div id="root"></div>` + `<script src="/assets/index-*.js">`».
В этом проекте такого **не может быть физически**:

- сборка идёт через `vite-plugin-singlefile` — весь JS/CSS инлайнится в
  `index.html`, файлов `/assets/index-*.js` не существует;
- в самом исходнике `index.html` внутри `<div id="root">` лежит статический
  контент главной (h1, список услуг, ссылки) — оболочка не пустая;
- все страницы обслуживаются serverless-функциями, которые подменяют
  title/description/canonical/OG/JSON-LD **и тело** на сервере.

Т.е. аудит написан по шаблону «типичного SPA», а не по нашему `view-source`.

## Реальная найденная проблема (закрыта в этом коммите)

**183 карточки товаров = 183 дубля тела главной.**

`api/seo.js` для `/kondicionery/:slug` и `/okna/:slug` патчил только `<head>`
(title, description, OG, canonical, Product JSON-LD) и **не трогал `<body>`**.
А в оболочке `index.html` внутри `<div id="root">` лежит статический блок
главной («Окна, кондиционеры и вентиляция в Иркутске — под ключ»). Итог: у всех
183 карточек исходный HTML тела был одинаковым. Ровно та же болезнь, из-за
которой статьи базы знаний когда-то перевели на серверную отрисовку
(комментарий в `vite.config.ts`: «иначе Яндекс считает их дублями главной»).

Что сделано в `api/seo.js`:

1. Добавлены `esc()` и `injectSeoBody()` (как в `api/page.ts`, функциональная
   форма `replace` — защита от `$`-последовательностей).
2. В ветку кондиционера — серверный `<main>`: хлебные крошки-ссылки, `h1` =
   имя модели (совпадает с клиентским), цена (+ BTU-вариант), описание,
   список фактов, телефон, **6 ссылок на похожие модели бренда** (перелинковка,
   которой раньше не было в исходном HTML вообще).
3. В ветку окон — то же: `h1` = заголовок решения, цена, факты, ссылки на 5
   других решений по остеклению **с каноническим регистром URL**
   (новое поле `siteSlug` в `windowCatalog`, совпадает с `src/data/windowsCatalog.ts`
   и sitemap).
4. Честный 404 для неизвестных slug сохранён.

Проверка регресса: `npm run test:seo-fn` — 6 тестов (карточка, нижний регистр,
BTU-вариант, окно, 404, legacy-id). Все зелёные.

## Инструментарий «до/после» (вместо предложенного аналитиком)

Аналитик предложил свой `check-seo.mjs`. Идея правильная, взяли за основу и
адаптировали под архитектуру (его вариант безнадёжно фейлился бы: проверка
«контент внутри `<div id="root">...</div><script`» не сработает, т.к. наш
скрипт инлайнен, а серверный контент лежит в `<main>` внутри root).

- `scripts/urls.txt` — 310 URL, сгенерировано из `public/sitemap.xml`.
- `node scripts/check-seo.mjs` — прогон по продакшену UA'ом YandexBot:
  HTTP-статус, уникальность title, description, canonical, `h1`, объём текста
  в root, **детектор тела-дубля главной**, внутренние ссылки, JSON-LD;
  плюс пробы: мусорный URL → 404+noindex, `/ventilyatsiya` → 301,
  `/окна/` → 301, `sitemap.xml` доступен. Код выхода 1 при любых проблемах —
  можно ставить шагом в CI.

Порядок действий:

```bash
# 1. «До»: зафиксировать состояние прода до выката коммита
node scripts/check-seo.mjs > before.txt   # ожидаем FAIL по карточкам: «тело = блок главной»

# 2. Выкатить коммит на Vercel (деплой из этой ветки)

# 3. «После»: повторить
node scripts/check-seo.mjs > after.txt    # карточки должны стать OK
```

## Что осталось за рамками (рекомендации, не блокеры)

1. **Единый источник каталога.** В `api/seo.js` каталог кондиционеров продублирован
   инлайном (177 моделей), а sitemap и клиент берут `src/components/CatalogConditioners.tsx`.
   Сейчас списки синхронны (0 расхождений), но при добавлении модели править надо
   два места — риск будущего рассинхрона «sitemap → 404». Уже существует
   `api/catalog-data.json`, генерируемый при сборке из единого источника, —
   стоит перевести `seo.js` на чтение из него.
2. Текстовый `<noscript>`-fallback в `index.html` (пара абзацев + телефон).
3. `/interier` — тематически чужой раздел; как уже отмечено в `vite.config.ts`,
   лучше на субдомен.
4. После выката: «Переобход» карточек в Яндекс.Вебмастере и проверка сниппетов
   цен для карточек (Product JSON-LD там уже был и остался).

## Ответ на вопрос «вариант А или Б»

Ни А, ни Б в виду уже не стоит: серверная отдача HTML реализована и работает,
внедрять поверх Puppeteer-пререндер — значит добавить вторую, конкурирующую
систему рендеринга. Правильный ход — устранять точечные дыры в существующем
серверном слое (что и сделано для карточек) и контролировать прод
автопроверкой `check:seo`.
